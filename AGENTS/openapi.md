# OpenAPI representations

OpenAPI 3.1 specifications for each form, **generated** from
`sql-migrations/` (the source of truth — see `spec.md` §3.1). One `.yaml`
file is produced per top-level SQL table entity, so that a form's resources
can be described, mocked, validated, and code-generated by any
OpenAPI-compatible tooling. Do not hand-edit; re-run the generator after
schema changes.

Slug: openapi

- Search pattern: `forms/*/sql-migrations/*.sql`
- Search pattern: `forms/*/openapi/*.yaml`
- Generator: `bin/openapi/generate-openapi-representations.py`

## What is OpenAPI?

OpenAPI is a vendor-neutral, language-agnostic specification format for
describing HTTP APIs. A single `.yaml` (or `.json`) document declares the
endpoints, parameters, request and response shapes, and reusable schema
components. The ecosystem around the spec is large: Swagger UI / Redoc
for interactive docs, Spectral for linting, Prism for mocking,
openapi-generator and oapi-codegen for typed client/server stubs in
dozens of languages.

Reference: <https://spec.openapis.org/oas/v3.1.0>

## Directory structure

One `.yaml` file per top-level SQL entity. The assessment's per-section
sub-tables (`assessment_<section>`) are folded into the single
`assessment.yaml` document, mirroring the behaviour of the FHIR R5, XML,
and protobuf generators — one form has exactly one `assessment.yaml`.

```
openapi/
  patient.yaml                    # Patient resource + CRUD endpoints
  assessment.yaml                 # Assessment resource (with merged sections)
  grade.yaml                      # Grade resource
  grading_fired_rule.yaml         # GradingFiredRule resource
  grading_additional_flag.yaml    # GradingAdditionalFlag resource
  ...                             # one .yaml per remaining SQL entity
```

The merged `Assessment` schema inlines every column from each
`assessment_<section>` child table at the top level, prefixing section
names on column-name collisions to keep every property unique.

## Document shape

Each YAML is a complete, self-contained OpenAPI 3.1 document for one
resource:

- `openapi: 3.1.0`
- `info` — title (`<Form Slug Titlecased> — <Resource>`), version
  (`1.0.0`), and description sourced from the SQL `COMMENT ON TABLE`.
- `paths` — five operations per resource:
  - `GET    /<plural>`        — list, with `limit` + `offset` query params
  - `POST   /<plural>`        — create
  - `GET    /<plural>/{id}`   — fetch by id
  - `PATCH  /<plural>/{id}`   — update
  - `DELETE /<plural>/{id}`   — soft-delete
- `components.schemas.<Resource>` — the single object schema describing
  every column in the source SQL table.

## Conventions

- Property names follow SQL `snake_case` — the schema describes the
  storage representation. Front-end TypeScript and Rust apply
  `serde(rename_all = "camelCase")` at their boundary.
- Resource names are `PascalCase` from the SQL table name (`patient` →
  `Patient`, `grading_fired_rule` → `GradingFiredRule`).
- Path segments are kebab-cased plurals of the table name
  (`patient_medication` → `/patient-medications`).
- A header comment marks the file as generated:
  `# Generated from sql-migrations/. Do not edit by hand.`
- A `# SOURCE: <table_name>` comment records the originating SQL
  table(s); the merged `assessment.yaml` lists every contributing
  `assessment_<section>` table.
- SQL `COMMENT ON COLUMN <table>.<column>` text is carried into each
  property's `description` field.
- `required` lists every `NOT NULL` column except `id` (server-assigned
  UUID default) and timestamps with `DEFAULT now()`.
- Foreign-key columns (e.g. `patient_id UUID REFERENCES patient(id)`)
  are emitted as plain `string` properties with `format: uuid`, not as
  `$ref` to a sibling resource. This keeps each YAML self-contained.

## SQL → OpenAPI type mapping

| SQL type                                    | OpenAPI                                  | Notes                                    |
| ------------------------------------------- | ---------------------------------------- | ---------------------------------------- |
| `UUID`                                      | `string` + `format: uuid`                | hyphenated lowercase UUIDv4              |
| `TIMESTAMPTZ`, `TIMESTAMP`                  | `string` + `format: date-time`           | ISO 8601 in UTC                          |
| `DATE`                                      | `string` + `format: date`                | ISO 8601 (`YYYY-MM-DD`)                  |
| `TIME`                                      | `string` + `format: time`                | ISO 8601 time                            |
| `BOOLEAN`                                   | `boolean`                                |                                          |
| `SMALLINT`, `INTEGER`, `INT`, `SERIAL`      | `integer` + `format: int32`              |                                          |
| `BIGINT`, `BIGSERIAL`                       | `integer` + `format: int64`              |                                          |
| `NUMERIC(p,s)`, `DECIMAL(p,s)`              | `number` + `format: double`              | precision/scale not expressible          |
| `REAL`                                      | `number` + `format: float`               |                                          |
| `DOUBLE PRECISION`                          | `number` + `format: double`              |                                          |
| `TEXT`                                      | `string`                                 |                                          |
| `VARCHAR(n)`, `CHAR(n)`                     | `string` + `maxLength: n`                | length carried into the schema           |
| `JSON`, `JSONB`                             | `object`                                 |                                          |
| `BYTEA`                                     | `string` + `format: byte`                | base64                                   |

Columns with `CHECK (... IN (...))` constraints become an OpenAPI string
`enum`, preserving every literal value declared in SQL (including the
empty-string sentinel that represents an unanswered question).

## Regenerate

Regenerate all `.yaml` files from the current SQL migrations:

```sh
python3 bin/openapi/generate-openapi-representations.py
```

## Verify

Lightweight structural check — every file should declare `openapi: 3.1.0`
and contain at least one `paths:` entry plus one schema component:

```sh
for f in forms/*/openapi/*.yaml; do
  grep -q '^openapi: 3.1.0$' "$f" || echo "missing openapi version: $f"
  grep -q '^paths:'           "$f" || echo "missing paths: $f"
  grep -q '^components:'      "$f" || echo "missing components: $f"
done
```

Validate as parseable YAML with the OpenAPI shape:

```sh
python3 -c "
import yaml, glob, sys
fails = 0
for f in sorted(glob.glob('forms/*/openapi/*.yaml')):
    d = yaml.safe_load(open(f))
    if d.get('openapi') != '3.1.0' or 'info' not in d or 'paths' not in d:
        print('FAIL', f); fails += 1
sys.exit(1 if fails else 0)
"
```

For full schema validation, run an OpenAPI linter such as Spectral:

```sh
npx --yes @stoplight/spectral-cli lint 'forms/*/openapi/*.yaml'
```

## Generate language bindings

Once `.yaml` files exist, generate native bindings or mock servers with
the openapi-generator or oapi-codegen toolchains:

```sh
# Typed TypeScript client
npx --yes @openapitools/openapi-generator-cli generate \
  -i forms/<slug>/openapi/patient.yaml \
  -g typescript-axios \
  -o gen/<slug>/patient-ts

# Rust client (reqwest)
openapi-generator generate \
  -i forms/<slug>/openapi/patient.yaml \
  -g rust \
  -o gen/<slug>/patient-rs

# Mock server with Prism
npx --yes @stoplight/prism-cli mock forms/<slug>/openapi/patient.yaml
```
