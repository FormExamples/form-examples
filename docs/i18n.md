# Internationalisation

> **Status: design + planned pilot, not yet implemented.** No form ships a
> translation layer today — there are no `assets/i18n/` directories or `.ftl`
> files in the corpus yet. This page documents the intended *pattern* and the
> first pilot. Full rollout across the 286 forms is future work, tracked in the
> root [`plan.md`](../plan.md) and [`tasks.md`](../tasks.md).

The system scope (spec.md §2) currently lists "internationalisation beyond
English + Welsh" as out of scope; the near-term goal is only to prove the shape
on one form.

## The pattern: message extraction behind a small layer

Front-ends today hard-code user-facing English strings inline in the wizard
markup and the report. The i18n pattern replaces those with **message keys
resolved through a thin lookup layer**, so the strings live in per-locale
message files rather than in components:

- UI strings are **extracted** out of the templates and given stable keys.
- Each locale gets a message catalogue under `assets/i18n/<locale>/main.ftl`,
  using the [Fluent](https://projectfluent.org/) (`.ftl`) format. The planned
  locales seeded in the root [`index.md`](../index.md) are `en-GB`, `en-US`,
  `cy-GB` (Welsh), and `de-DE`.
- A **minimal message layer** (a `t(key, args)`-style helper) resolves a key to
  the active locale's string at render time, with the source locale as the
  fallback.

Deliberately kept small: no framework lock-in, no build-time codegen beyond
loading the `.ftl` catalogues, and the message layer is the only new dependency
surface. The keys are the contract; the catalogues are data.

## What stays out of the message layer

Only **presentation** strings are translated. The following are locale-invariant
and must not be moved behind the layer:

- Stable identifiers: `rule_id`, `flag_id`, enum values (the SQL `CHECK` lists).
- The data model itself — column names, the JSON API's camelCase properties.
- Clinical scoring thresholds and bands.

In other words, i18n is a front-end presentation concern layered on top of an
unchanged [data model](data-model.md) and [scoring engine](scoring-engines.md);
translating a form must never change what it computes or stores.

## The English/Welsh pilot

The first pilot targets the Cymraeg-relevant form,
`forms/medical-language-speaking-assessment-for-cymraeg`, because Welsh-language
provision is intrinsic to that form's purpose (the Welsh Language Act context).
The pilot's shape, per [`plan.md`](../plan.md) and [`tasks.md`](../tasks.md):

1. Extract the UI strings of one Svelte front-end behind the minimal message
   layer.
2. Ship `en-GB` + `cy-GB` catalogues for the Cymraeg form to prove the round
   trip end to end.
3. Write up the resulting pattern (this document).
4. **Defer** the full rollout across all forms and the additional locales — that
   remains recorded as future work, not a commitment.

## Why not everywhere yet

Rolling i18n across 286 forms is a large, mechanical extraction that wants a
generator and a drift gate (the same discipline as the rest of the repo — see
[Generator pipeline](generator-pipeline.md) and [Verification](verification.md))
before it is worth doing at scale. The pilot exists to validate the message-layer
shape and the Fluent catalogue layout first, so that a future generator can
extract keys and scaffold catalogues consistently.
