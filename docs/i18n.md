## Reference implementation (the Cymraeg pilot)

Living in
[`forms/medical-language-speaking-assessment-for-cymraeg/front-end-with-svelte/`](../forms/medical-language-speaking-assessment-for-cymraeg/front-end-with-svelte/),
the pilot translates only the **front-end chrome** — the welcome page
(`+page.svelte`) and the layout nav (`+layout.svelte`) — into English and
Welsh. It mirrors the existing theme-switcher convention exactly, so the two
concerns (theme, locale) read the same way:

- **Message catalogue** — `src/lib/i18n/messages.ts` is a typed
  `Record<Locale, Messages>` (`{ en, cy }`) keyed by semantic names
  (`startNewAssessment`, `purpose`, `documentation`, …). A `Messages`
  interface is the contract every locale must satisfy, so a missing or renamed
  key is a `npm run check` type error rather than a runtime blank. `en` is the
  source locale and the fallback.
- **Locale store** — `src/lib/i18n/locale.svelte.ts` is a Svelte 5 runes store
  (`$state` current locale, default `en`), persisted to localStorage under
  `medical-language-speaking-assessment-for-cymraeg.locale.v1` via
  `$effect.root`, exactly like the theme store. It exposes a `t(key)` helper
  that resolves a key to the active locale's string (with the `en` fallback),
  and mirrors the choice onto `<html lang>` (`en-GB` / `cy`) so assistive
  technology announces the correct language.
- **Switcher** — `src/lib/components/ui/LocaleChooser.svelte` is the headless
  sibling of `ThemeChooser`, a single-glyph button + listbox reusing the Lily
  headless button+listbox contract so the two nav controls render identically.
  It sits next to the theme switcher in the layout nav and offers
  **English / Cymraeg**.

Chosen deliberately over the Fluent `.ftl` sketch below: a plain typed TS
object needs no new runtime dependency, gives compile-time key checking, and
tree-shakes into the existing SvelteKit build. A future generator can still emit
`.ftl` (or any format) behind the same `t(key)` seam — the keys are the
contract.

**Explicitly out of scope for the pilot:** the step components and clinical
questions (`Step1…`–`Step5…`, role-play prompts, criteria wording) and the
scoring engine are **not** translated — only the shell. Extending coverage to
the wizard body is part of the deferred rollout.

## The pattern: message extraction behind a small layer

Front-ends hard-code user-facing English strings inline in the wizard markup and
the report. The i18n pattern replaces those with **message keys resolved through
a thin lookup layer**, so the strings live in per-locale catalogues rather than
in components:

- UI strings are **extracted** out of the templates and given stable, semantic
  keys.
- Each locale gets a catalogue. In the shipped pilot this is a typed TS object
  (`messages.ts`, `{ en, cy }`); a future generator could equally emit
  [Fluent](https://projectfluent.org/) (`.ftl`) files under
  `assets/i18n/<locale>/main.ftl`. The locales seeded in the root
  [`index.md`](../index.md) are `en-GB`, `en-US`, `cy-GB` (Welsh), and `de-DE`;
  the pilot ships `en-GB` + `cy`.
- A **minimal message layer** (the `t(key)` helper on the locale store) resolves
  a key to the active locale's string at render time, with the source locale
  (`en`) as the fallback.

Deliberately kept small: no framework lock-in, no new runtime dependency, and
the message layer is the only new surface. The keys are the contract; the
catalogues are data.

## What stays out of the message layer

Only **presentation** strings are translated. The following are locale-invariant
and must not be moved behind the layer:

- Stable identifiers: `rule_id`, `flag_id`, enum values (the SQL `CHECK` lists).
- The data model itself — column names, the JSON API's camelCase properties.
- Clinical scoring thresholds and bands.

In other words, i18n is a front-end presentation concern layered on top of an
unchanged [data model](data-model.md) and [scoring engine](scoring-engines.md);
translating a form must never change what it computes or stores.

## The English/Welsh pilot

The pilot targets the Cymraeg-relevant form,
`forms/medical-language-speaking-assessment-for-cymraeg`, because Welsh-language
provision is intrinsic to that form's purpose (the Welsh Language Act context).
Its four-step shape, per [`plan.md`](../plan.md) and [`tasks.md`](../tasks.md):

1. **Done** — extracted the UI chrome of the Svelte front-end (welcome page +
   layout nav) behind the minimal message layer.
2. **Done** — shipped `en` (en-GB) + `cy` catalogues for the shell to prove the
   round trip end to end, with a nav locale switcher and a correct `<html lang>`.
3. **Done** — wrote up the resulting pattern (this document; see *Reference
   implementation* above).
4. **Deferred** — the full rollout across all forms, the wizard/clinical body of
   this form, and the additional locales (`en-US`, `de-DE`) remain recorded as
   future work, not a commitment.

## Why not everywhere yet

Rolling i18n across 347 forms is a large, mechanical extraction that wants a
generator and a drift gate (the same discipline as the rest of the repo — see
[Generator pipeline](generator-pipeline.md) and [Verification](verification.md))
before it is worth doing at scale. The shipped pilot validates the message-layer
shape (a typed catalogue behind a `t(key)` seam) so that a future generator can
extract keys and scaffold catalogues consistently.

For how work lands in the repo, see [`CONTRIBUTING.md`](../CONTRIBUTING.md).
